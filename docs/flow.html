Alur Operasi STOCKWISE

Bagaimana satu permintaan barang bergerak dari karyawan sampai stok benar-benar berubah di gudang — siapa yang bertindak di tiap tahap, apa syaratnya, dan kapan angka actual_qty naik atau turun.

Backend: Laravel + MySQL Frontend: React 7 peran RBAC 2 site · SIG-SDA, SIG-BPN
00

Peta besar: kapan stok berubah

STOCKWISE memisahkan tiga angka: actual (fisik di rak), reserved (sudah dijanjikan ke request), dan available = actual − reserved. Setiap perubahan stok ditulis sebagai baris stock_movements di dalam satu transaksi database — tabel itu tidak pernah diubah langsung.

Aturan mutlak. Stok turun saat pengambilan NPBG, naik saat penerimaan RI dikonfirmasi (bukan saat RI dibuat), dan disesuaikan hanya setelah opname disetujui Admin Gudang. Anak Gudang tidak pernah mengubah actual langsung.
01

Request barang

Karyawan membuat permintaan barang. Nomor dibuat otomatis mengikuti pola REQ/<SITE>/<YY>/<BULAN-ROMAWI>/<URUT> — misalnya REQ/SDA/26/IX/001.

Aktor
Karyawan (pemilik request)
Pemicu
Kirim form dari status DRAFT
Efek
Snapshot stok & projected per baris, notifikasi Admin Gudang

Isi form

Diisi peminta

  • Tanggal — default hari ini
  • Nama Peminta — default nama akun, bisa diganti
  • WhatsApp Peminta — terisi otomatis dari nomor akun
  • Nama Barang — pilih dari master atau ketik bebas
  • QTY
  • UOM / satuan — ikut master barang; manual jika baris bebas
  • Keterangan & Catatan

Diisi sistem / Admin Gudang

  • Lokasi permintaan — otomatis dari IP: Jaringan Kantor / Di Luar Kantor
  • Snapshot stok sistem, safety stock, projected — otomatis saat submit & review
  • No NPBG — Admin Gudang; terisi otomatis saat NPBG dibuat
  • Nomor PPB — Admin Gudang; terisi otomatis saat PPB dibuat

02

Review & cek fisik gudang

Admin Gudang mengambil request (SUBMITTED → UNDER_REVIEW). Sistem menampilkan stok sistem terakhir per baris. Sebelum reservasi, gudang wajib memverifikasi bahwa barang benar-benar ada secara fisik sesuai sistem.

Aktor
Admin Gudang / Anak Gudang
Pemicu
Cek fisik per baris: VERIFIED_MATCH atau VERIFIED_MISMATCH
Efek
Hitung projected & flag di bawah safety stock; mismatch memblokir reservasi

Reservasi stok

Saat Admin Gudang menekan Reserve, untuk tiap baris yang stoknya cukup dibuat movement RESERVATION dan baris stock_reservations berstatus ACTIVE (kedaluwarsa default 14 hari). actual tidak berubah; reserved naik, sehingga available turun. Kekurangan pada baris apa pun membuat status request menjadi PARTIAL atau NEED_PURCHASE.

03

NPBG & pengambilan barang

Dari request RESERVED / PARTIAL, Admin Gudang membuat NPBG (Nota Pengeluaran Barang Gudang). Nomornya otomatis mengisi kolom No NPBG di request. Barang disiapkan fisik oleh Lapangan Gudang, lalu diambil peminta dengan tanda tangan.

Aktor
Admin Gudang (buat) · Lapangan Gudang (siapkan & serahkan)
Pemicu
Pengambilan: verifikasi peminta + barang + qty, tanda tangan
Efek
STOCK_OUT per baris — actual−, reserved−, reservasi → CONSUMED
04

Pengadaan: PPB → PO → Penerimaan

Kekurangan stok memicu PPB (Permintaan Pembelian Barang). Setelah disetujui, Purchasing membuat Purchase Order ke vendor. Barang datang dicatat sebagai Penerimaan (RI), dan stok baru bertambah ketika RI dikonfirmasi.

Aktor
Admin Gudang (PPB) · Purchasing (PO, RI)
Pemicu
PPB approve → PO approve & kirim → RI confirm
Efek
Stok naik RECEIVING hanya saat RI CONFIRMED
DokumenStatusCatatan
PPBDRAFT → SUBMITTED → REVIEW → APPROVEDReject → CANCELLED. Amend / close via ppb_amendments.
Purchase OrderDRAFT → APPROVED → SENT → PARTIAL_RECEIVED → RECEIVEDBatal hanya sebelum ada RI. qty_received ikut RI yang CONFIRMED.
Receiving (RI)CHECKING → CONFIRMEDSebagian ditolak → catat RI lain. Semua ditolak → REJECTED. Stok tidak bertambah sebelum CONFIRMED.
05

Stock Opname

Opname dijadwalkan per gudang. Anak Gudang menghitung fisik tiap baris, lalu submit. Admin Gudang mereview per item. Hanya item yang disetujui dan berselisih yang mengubah actual_qty — lewat stock_adjustments + STOCK_ADJUSTMENT.

Aktor
Anak Gudang (hitung) · Admin Gudang (review)
Pemicu
Per item: APPROVED / REJECTED / RECOUNT
Efek
APPROVED + selisih ≠ 0 → actual_qty = physical_qty

Mesin hitung: safety stock & prioritas

Semua di backend (StockwiseEngine). Frontend hanya menampilkan hasil. sisa_stok = available = actual − reserved.

selisih = sisa_stok − safety_stock

status:
  sisa_stok == 0 dan safety_stock == 0 → BEP
  selisih ≥ 0 → AMAN
  selain itu → TIDAK_AMAN

deficit = max(safety_stock − sisa_stok, 0)

priority_score = // hanya bila TIDAK_AMAN
  (deficit × 2.0) + (lead_time × 1.0)

priority_level:
  AMAN / BEP → LOW
  TIDAK_AMAN dan (deficit ≥ median_deficit atau lead_time ≥ threshold) → HIGH
  TIDAK_AMAN lainnya → MEDIUM

Parameter dataset dihitung ulang tiap malam & setelah opname/penerimaan besar: lead_time_threshold = persentil-75 lead time item aktif (fallback 14), dan median_deficit dari semua item TIDAK_AMAN. Saat membuat / mereview request & PPB: projected_stock = available − qty_diminta, dan below_safety bila projected_stock < safety_stock.
